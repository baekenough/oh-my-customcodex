# v1.0.14 Release Plan

## Goal

Make the packaged Node Web runtime retain persistent evaluation sessions, remember its real lifecycle endpoint across CLI processes, and open that endpoint through the operating system browser.

## Release Unit

| Issue | Priority | Outcome |
| --- | --- | --- |
| #1599 | P1 | Replace the silent Bun-only evaluation database read with an explicit Node-native adapter, canonical Codex storage, legacy read-only compatibility, deterministic deduplication, and visible diagnostics. |
| #1600 | P2 | Persist a versioned, atomic serve state containing the actual PID, port, project root, and start time while remaining compatible with legacy numeric PID files. |
| #1601 | P2 | Make `web open` launch the persisted server URL with platform-native, shell-free argv and return a clear failure when the browser cannot be launched. |

## Constraints

- Add no runtime dependency and retain the published Node 20.17 compatibility contract.
- Prefer dynamically probed `node:sqlite` on Node 22.13+; use a bounded Bun subprocess only when that capability is unavailable, and surface a structured diagnostic when neither runtime can read SQLite.
- Write new evaluation data only under `~/.oh-my-customcodex`; read legacy paths without mutating them.
- Do not let an empty canonical database suppress compatible legacy database rows.
- Store serve state through a mode-`0600` sibling temporary file plus atomic rename; clean stale and legacy state safely.
- Pass browser URLs as argv with `shell: false`; never interpolate them into a command string.
- Keep #1599 and #1600/#1601 implementation ownership separate, with the package-contract verifier integrated centrally.

## Implementation

1. Introduce an asynchronous evaluation database adapter with Node SQLite and bounded Bun fallback backends, structured diagnostics, canonical/legacy path merging, and stable session identity derived from `session_id` or `session_ppid`.
2. Move JSON evaluation writes to the canonical Codex directory while merging canonical and legacy reads; expose database diagnostics on evaluation pages.
3. Replace PID-only lifecycle storage with a versioned serve-state reader/writer that accepts legacy numeric files and returns the authoritative running port.
4. Route `web status`, `web open`, start, and stop through that state; implement injectable platform browser commands and exact failure exit semantics.
5. Extend package-contract verification with a fixture evaluation database, cross-process custom-port lifecycle checks, and browser-open command assertions.

## Verification

- Targeted evaluation reader/routes/UI, lifecycle, web command, and package-contract tests.
- Node 20 fallback and Node 22+ native SQLite coverage where the runtime is available.
- Root lint, TypeScript checks, full tests, production build, and installed-tarball package-contract verification.
- PR checks green, merge to `develop`, tag `v1.0.14`, npm/GitHub Packages publication, GitHub Release, #1599/#1600/#1601 and milestone closure, and clean registry-install smoke.

## Stop Condition

The release is complete only when a clean installed Node Web server displays a fixture session instead of silently dropping it, incompatible SQLite runtimes produce a visible diagnostic, a custom port survives independent CLI invocations and stale cleanup, `web open` launches the exact persisted URL or fails non-zero, both registries expose `1.0.14`, and all three issues plus the v1.0.14 milestone are closed.
