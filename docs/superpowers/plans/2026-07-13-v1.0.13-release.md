# v1.0.13 Release Plan

## Goal

Make linked-worktree lockfiles describe the same main-checkout Codex hook assets that Codex discovers, executes, diagnoses, and updates.

## Release Unit

| Issue | Priority | Outcome |
| --- | --- | --- |
| #1625 | P1 | Track authoritative native hook registry and active scripts through lockfile generation, drift diagnosis, synchronization, snapshot finalization, and update regeneration without exposing path traversal or link escapes. |

## Constraints

- Keep `.omcodex.lock.json` in the requested checkout while allowing individual entries to identify the trusted Codex project root.
- Preserve ordinary checkout and fail-closed repository shapes such as separate Git directories, submodules, bare repositories, and non-Git directories.
- Keep lockfile keys project-relative; reject absolute paths, traversal, unknown roots, symlinks, and multi-link files.
- Reuse the authoritative root resolver introduced for native hook discovery instead of adding a second Git-worktree heuristic.
- Preserve user-modified native hook content during updates and refresh only unmodified managed assets.

## Implementation

1. Add a backwards-compatible lockfile entry root discriminator and one safe entry-path resolver.
2. Generate non-hook entries from the requested checkout and native hook entries from the authoritative Codex project root.
3. Route doctor drift checks through the same resolver; let sync, snapshot, and updater inherit the canonical generator.
4. Add linked-worktree, fail-closed repository-shape, symlink, hardlink, drift, snapshot, and update regressions.

## Verification

- Targeted lockfile, Codex hook integration, doctor, snapshot, sync, and updater tests.
- Root lint, TypeScript checks, full tests, production build, and package-contract verification.
- PR checks green, merge to `develop`, tag `v1.0.13`, npm/GitHub Packages publication, GitHub Release, #1625 and milestone closure, and clean registry-install smoke.

## Stop Condition

The release is complete only when a real standard linked worktree records the authoritative main-checkout registry and active scripts, drift and updates operate on those same files, unsafe lockfile paths cannot escape either trusted root, both registries expose `1.0.13`, and #1625 plus the v1.0.13 milestone are closed.
