# R005: Optimization Guide

Provides guidelines for efficiency, token optimization, and task batching — applied selectively where benefit is clear and measurable.

## Overview

Optimization should be applied to repetitive or bottlenecked operations. Strategies include parallelization, caching, lazy loading, and token compression. Readability always takes precedence — no optimization without measurable benefit.

## Priority

**MAY** — Optional. Apply when there is a clear, measurable gain. Never at the cost of readability or correctness.

## Key Requirements

**Efficiency strategies:**

| Strategy | When | Example |
|----------|------|---------|
| Parallel | 3+ independent I/O tasks | Read multiple files simultaneously |
| Caching | Same data accessed repeatedly | Cache file contents, reuse search results |
| Lazy Loading | Large datasets, partial use | Read only needed files, stream results |

**Token optimization:**
- Include only necessary info, remove duplicates, use summaries
- Concise expressions, minimize code blocks, no unnecessary repetition

**Task optimization:**
- **Batch**: Group similar tasks (edit 10 files at once)
- **Incremental**: Process only changed parts

**When to optimize:**

| Do | Don't |
|----|-------|
| Repetitive tasks, clear bottleneck, measurable gain | One-time tasks, already fast, complexity > benefit |

**Context optimization via HTML comments (v2.1.72+):** Move model-unnecessary metadata into HTML comments in `.md` files to reduce context token usage.

## Claude v2.1.210 auto-background and Grep compatibility

Use absolute paths for dependent follow-up commands. Grep content mode also no longer reports `No matches found` only because pagination moved past the final result. These are provider-owned Claude behaviors; active Codex/OMX tool output remains the evidence source.

## Claude v2.1.212 MCP auto-background compatibility

Claude Code v2.1.212 moves MCP calls longer than two minutes into background execution by default; `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` changes or disables the threshold. Do not call that provider transition a hang. Codex/OMX still requires the active tool's terminal result.

## Display-Pipe Exit Status

Output truncation is not verification. In `producer | head`, `producer | tail`, or `producer | tee`, a successful consumer can hide a failed producer. Keep dependent release gates sequential and inspect the producer's status directly.

If a display pipe is unavoidable, run it under explicit Bash with `set -o pipefail` and capture `${PIPESTATUS[0]}` before any later command. Do not reuse Bash pipeline-status syntax in zsh, and never let `head`, `tail`, or `tee` override a non-zero producer result.
