# R012: Native HUD and Status Line Rules

Defines the separate Codex/OMX surfaces for workflow state, persistent TUI
status, and bounded hook notifications.

## Overview

OMX HUD is the harness-owned workflow and team status surface. The Codex TUI
footer is a user preference selected with `/statusline` or configured under
`[tui].status_line` in `config.toml`. A project-scoped OMX runtime mirrors the
project's `.codex/config.toml` into its isolated `CODEX_HOME`, so init and update
seed a native default only when that project configuration has no
`status_line` assignment. Hook events provide compact notifications for
parallel or long-running work without replacing either native surface.

## Priority

**SHOULD** — Use native status surfaces consistently and preserve user-owned
Codex footer configuration.

## Key Requirements

| Surface | Owner | Purpose |
|---------|-------|---------|
| OMX HUD | `omx hud` / `omx hud --tmux` | Live workflow, team, goal, and session state |
| Codex TUI status line | `/statusline` / `[tui].status_line` | User-selected persistent footer items |
| Harness hook events | Native Codex hook registry | Bounded event notifications |

- Seed the native default only when `[tui].status_line` is absent from the
  project `.codex/config.toml` mirrored into isolated `CODEX_HOME`.
- Preserve an existing custom assignment, including an explicitly empty array,
  byte-for-byte.
- Fail closed if `.codex/config.toml` cannot be read or rewritten safely because
  of a symlink, hardlink, identity race, or stale ready assessment.
- Do not install `.codex/statusline.sh`.
- Do not write Claude `statusLine` JSON to `.codex/settings.local.json`.
- Treat OMX runtime state as authoritative; hook messages must not invent
  progress or completion.

## Native Footer Provisioning

The absence-only project default includes `model-with-reasoning`, `git-branch`,
`context-remaining`, `total-input-tokens`, `total-output-tokens`,
`five-hour-limit`, and `weekly-limit`. It exists so the Codex footer remains
available after OMX creates an isolated runtime mirror; it is not a
harness-owned replacement for an explicit preference.

If the project already declares `[tui].status_line`, init and update leave the
assignment and surrounding TOML formatting unchanged. An explicit `[]` is a
valid preference and must not be treated as missing. Provisioning uses the same
safe configuration boundary as OMX readiness: unsafe paths, identity races, and
a config that disappears after a ready assessment stop the operation instead of
following an external target, rerunning setup, or silently claiming success.
Required changes are written only through the verified config descriptor,
followed by file sync and exact readback, so a path swap cannot redirect the
write to a replacement inode. Synchronous write failures attempt exact rollback
and expose uncertain recovery explicitly. The descriptor-bound rewrite
preserves existing inode metadata but does not claim crash atomicity across
process termination or power loss.

## Claude Compatibility Boundary

`templates/.claude/statusline.sh` remains only as an explicit Claude Code
compatibility asset for the Claude JSON-stdin protocol. Claude-only footer
links, usage views, notification events, and `refreshInterval` behavior must
not be described as Codex/OMX runtime state.

## Claude v2.1.202-v2.1.208 status compatibility

Claude Code v2.1.202 adds `workflow.run_id` and `workflow.name` to telemetry for workflow-spawned agents. Claude Code v2.1.208 keeps completed background agents in `/tasks`, fixes temporary 200k context display, and prevents `/release-notes` from polluting conversation context. These are Claude status and context surfaces; OMX HUD and the native Codex statusline remain authoritative here.

## External Status Surface Conflicts

Use one persistent footer owner. An explicitly selected compatibility footer
must not run beside the Codex native footer. OMX HUD can remain enabled because
it reports workflow state through a separate surface.
