# R009: Parallel Execution Rules

Two or more independent tasks MUST execute in parallel. Sequential execution of parallelizable tasks is a violation.

## Overview

Parallel execution maximizes throughput and reduces wall-clock time. Before spawning 2+ parallel agents, the Agent Teams eligibility check ([[r018]]) must be performed — Agent Teams may be required instead of raw Agent tool calls. Adaptive splitting handles stalled agents at runtime.

## Priority

**MUST** — Enforced. Sequential execution of independent tasks requires correction. PostCompact hook re-injects this rule.

## Key Requirements

**Independence criteria (MUST parallelize):**
- No shared mutable state between tasks
- No sequential dependencies
- Each completes independently

**Agent Teams gate:** Quick rule — 3+ agents OR review cycle OR 2+ issues in same batch → use Agent Teams ([[r018]]).

**Execution limits:**

| Rule | Detail |
|------|--------|
| Max instances | 5 concurrent (soft default: 4) |
| Large tasks (>3 min) | MUST split into parallel sub-tasks |
| Orchestrator | Must stay singleton, never parallelized |

**Adaptive parallel splitting:** When an agent takes 2x+ longer than peers, spawn independent follow-up tasks immediately without canceling the stalled agent.

**LLM batch output budget:** For N-item scoring/classification/extraction calls that emit structured output, pre-compute N × per-item output tokens before the call. Chunk variable-size lists (default ≤40 items) and constrain per-item output rather than only raising `max_tokens`, because mid-JSON truncation can look like a successful call until parsing fails.

Detailed detection, stability, and announcement examples are preserved in HTML `DETAIL` blocks in the source rule and can be loaded with a direct Read when needed.

**Display format:**
```
[1] mgr-creator:sonnet → Create Go agent
[2] lang-python-expert:sonnet → Review Python code
```

**Result aggregation:**
```
[Summary] {succeeded}/{total} tasks completed
  ✓ agent-1: success
  ✗ agent-2: failed (reason)
```

## Claude v2.1.202 workflow-size compatibility

Claude Code v2.1.202 exposes small, medium, and large Dynamic workflow size choices. The choice is advisory rather than an enforced concurrency cap, so compatibility workflows must inspect actual capacity. Codex/OMX parallel execution continues to use the active slot limit and R009 independence checks.

## Verify-Bash + action-delegate asymmetry

When a parallel batch contains a verification Bash call and an action delegate, the delegate is easy to announce but omit. Dispatch BOTH calls in the SAME message; running verification now and silently postponing the Agent/Workflow action violates announce-execution consistency.

## Enforcement

Advisory PostToolUse hook + PostCompact re-injection per [[r021]].

## Relationships

- **Related rules**: [[r008]], [[r010]], [[r018]]
- **Affects**: All multi-task operations, batch workflows, research skills

## Parallel Feature Integration Gate

Per-subagent "build green" does not prove integrated runtime correctness. When parallel feature agents edit interdependent code (shared singletons, navigation stacks, API contracts, shared config, generated/template mirrors), the orchestrator must run an aggregate build plus runtime/smoke verification after merging all lanes and before declaring done.


## Fable 5 Long-Lived Lane Note

Fable 5 can be reused for a coherent bounded lane across multiple steps, but this does not weaken R009. Independent work still parallelizes; the Fable-specific option is to avoid unnecessary short-lived splits inside one lane when the lane has a clear boundary and evidence requirement.
