# R020: Completion Verification Rules

Before declaring any task `[Done]`, verify actual completion against task-type-specific criteria. Claiming completion without verification is a violation.

## Overview

False completion declarations erode trust and cause downstream failures. "Ran the command" does not equal "succeeded." Each task type has explicit required verifications that must be confirmed before `[Done]` is declared.

## Priority

**MUST** — Non-negotiable. Declaring `[Done]` without verification evidence is a violation requiring immediate correction.

## Key Requirements

**Task-type completion matrix:**

| Task Type | Required Verification |
|-----------|----------------------|
| Release | All issues closed, version bumped, PR merged, GitHub Release created, external automation verified |
| Implementation | Code compiles, tests pass, no TODO markers left |
| UI/Frontend | Browser or screenshot smoke evidence collected; target viewport layout is checked for overlap |
| Documentation | Links valid, counts accurate, cross-references updated |
| Git Operations | Operation succeeded (exit code checked), working tree clean |
| Code Review | All findings addressed or explicitly deferred |
| Agent/Skill Creation | Frontmatter valid, referenced skills exist, routing updated |

**Completion contract format (complex tasks):**
```
[Contract] Task: {name}
├── Criterion 1: {specific, verifiable condition}
└── Criterion N: {specific, verifiable condition}
```

**Done declaration format:**
```
[Done] Task: {name}
├── ✓ Criterion 1: {evidence}
└── ✓ Criterion N: {evidence}
```

**Common false completion patterns to avoid:**

| Pattern | Reality | Fix |
|---------|---------|-----|
| "Command executed" | Terminal exit code not checked | Read the tool's numeric terminal result; poll an active session |
| "File created" | Content not verified | Read file back, verify content |
| "Tests pass" | Only ran subset | Run full test suite |
| "Auto-publish ran" | External workflow not confirmed | Check `gh run list` for triggered jobs |
| "Subagent reported pre-existing" | Not verified against baseline | Compare develop branch directly |
| "Continued old plan after user interrupt" | Newest instruction has priority | Re-rank work and update completion contract before closing |

## Tool-Call Payload Completeness

Tool-call completion includes payload completeness at invocation time. Do not treat "I announced the tool" or "I attempted the call" as sufficient when schema-required fields are missing. R008 owns the canonical required-parameter check; R020 cross-checks that such malformed calls are not counted as verified progress or completion evidence.

## Diagnostic Hypothesis Verification

When a diagnosis would cause a permanent workflow, rule, template, or release-process change, the diagnosis must be treated as a hypothesis until directly verified. Record the symptom, proposed root cause, direct evidence, and at least one plausible alternative before merging the permanent change.

This specifically guards release workflows from repeating the pattern where an initial `E403` or clean-checkout failure is attributed to the wrong root cause without registry, CI, or source evidence.

### Variant: Parallel Read + Permanent-Change Dispatch

Do not batch diagnostic `Read` or log inspection with permanent issue/fix dispatch in the same parallel batch when the write depends on the diagnostic result. A file read, CI log check, or source inspection must complete before creating issues, delegating fixes, or editing workflows/rules/templates based on that evidence.

R009 parallel execution applies only to independent tasks. Diagnostic evidence and the permanent change that depends on it are sequential, not independent. This prevents stale or speculative issue, PR, and commit records when the later read reveals a different root cause.

## Evidence-Joined Mutation Completion

For issue triage, release lifecycle, and other external-state automation, an intent summary is not mutation authorization. Complete an evidence join first, then persist a reviewed local mutation draft containing explicit preconditions, desired state, stable action IDs, evidence references, rationale, and repository identity.

At the mutation barrier, reject stale preconditions and unknown action kinds, skip already-satisfied actions idempotently, and verify authoritative API or registry state. A write counts as complete only after direct readback confirms its desired state.


## Workflow Script Sanity Check

Generated workflow and release shell snippets must be sanity-checked before execution or registration. Compound verification gates should start with `set -euo pipefail`, because `set -o pipefail` alone does not halt later sequential checks after an earlier command fails. zsh/bash snippets must also avoid reserved or special variable names such as `status`, `path`, and `argv`; use specific names like `run_status`, `cmd_path`, or `args`.

## Managed Shell Advisor and Code Mode Results

Autonomous implementation, release, and R020 gates first run `omcustomcodex doctor --require-shell-advisor`. Only the exact package-managed Bash advisor may satisfy this prerequisite: the registry identity and both scripts must match packaged bytes, and Codex runtime discovery must report the same project entry enabled and trusted or managed. General OMX/plugin readiness is insufficient.

Missing assets use `omcustomcodex update --hooks`. Modified registry or script assets require review and backup before `omcustomcodex update --hooks --force-overwrite-all`. For an inactive result, verify both the supported user-level feature setting and project trust through `/hooks`, because an untrusted linked worktree may appear inactive. Approval remains manual; automation must never write trust state.

Official Codex routes Code Mode nested `tools.exec_command` through canonical Bash `PreToolUse`, so completion code must not add an outer parser, new matcher, or widened native-tool set. JavaScript reads the completed tool object's numeric `exit_code`; when only a session id exists, it polls to a terminal result. Pass-looking stdout and appended probes such as `status=$?` are not success evidence. The hook remains advisory even though the readiness preflight fails closed.

## Test-Skip Is Not Completion

Skipping tests, lowering coverage thresholds, narrowing the test command, or marking suites as TODO can be temporary containment only. Completion still requires a linked issue, owner, reproduction command, precise skipped scope, and a follow-up that restores the skipped coverage.

## Interrupt Priority Re-Ordering

When a new user message arrives mid-work, the completion contract must be recalculated against the newest instruction. Conflicting old work stops or re-routes; narrowed scope is reported as narrowed; added requirements become completion criteria before `[Done]`.

## Subagent Self-Report Verification

Subagents may claim failures were "pre-existing" to avoid blame. The orchestrator must verify such claims before accepting them.

**CC v2.1.200+ compatibility:** Claude subagents rate-limited before emitting any output now return a clean failure instead of a silent empty result. This reduces another false-success/silent-empty path, but Codex/OMX workflows still need deterministic repository/test/validation/registry/API evidence before accepting completion.

| Subagent Claim | Verification Method |
|----------------|---------------------|
| "This bug pre-existed the change" | `git diff develop` on the relevant file |
| "That test was already failing" | Run test suite on develop branch |
| "External workflow already triggered" | `gh run list --workflow=<name>` |
| "Issue was already closed" | Check GitHub issue timeline directly |

**Rule:** "Pre-existing" claims are hypotheses, not facts. Verify before accepting.

The v0.87.2-v0.88.0 issue #869 incident remains the provenance for this pattern. Its originating memory files were later consolidated or removed and must not be cited as current live paths.

## Autonomous Mode Entry Checklist

When entering autonomous mode (user grants extended execution without per-step confirmation), perform this inventory BEFORE first action:

1. **Workflow inventory**: `ls .github/workflows/` — identify auto-publish, auto-tag, release, docs-sync, CI workflows
2. **Recent runs**: `gh run list --limit 10` — check success/failure patterns of automated workflows
3. **External publish targets**: Check if npm/PyPI/Docker Hub/GitHub Releases are auto-triggered on merge
4. **Manual intervention points**: Identify which steps require human approval vs. fully automated
5. **Cross-reference with task**: Which workflows will the planned work trigger?

Record findings in session context. Failure to inventory automation is a R020 violation (unknown external state = unverifiable completion).

## Claude v2.1.211 background-agent compatibility

Claude Code v2.1.211 reports still-running background agent status and waits for real completion instead of fabricating results. R020 still requires repository, test, registry, and API evidence in Codex/OMX.

## CI Job Conclusion vs Actual Execution

A required CI job can report success through the documentation-only fast path. When `full_ci=false`, inspect duration and the `Report documentation-only fast path` step log before saying the expensive steps executed.

## Enforcement

Prompt-based per [[r021]]. Integrates with [[r003]] `[Done]` format and [[r017]] structural verification.

## Interrupt ≠ Prior-Request Cancellation

If the first message after an interrupt is ambiguous, do not assume the prior request was cancelled. Preserve non-destructive prior context and clarify once when the new message cannot be classified as clear continuation/correction/new work.

**Safety carve-out:** if interrupted work is destructive or irreversible (`git reset --hard`, `git clean -fd`, broad `rm`, force push, tunnel/DNS/k8s/infra deletion, production state changes), halt first and require explicit re-authorization before resuming.

## Config-Schema-Before-Edit (v0.5.22)

When a configuration edit touches fields that participate in an override, precedence, inheritance, provider, endpoint, credential, or multi-key chain (for example provider + `base_url`), read the full config schema and precedence chain before planning the edit.

| Forbidden | Required |
|-----------|----------|
| Plan a provider/endpoint switch without reading the override chain | Read schema and precedence → enumerate every touched field, including `base_url` → then plan |

Origin: Codex port #1495 from upstream #1327; a provider switch nearly left `base_url` pointing at the previous provider.

## Proxy Signal vs Canonical Ground-Truth

When diagnosing pipeline or data state, verify the canonical store (authoritative DB/system-of-record) before characterizing state from a secondary proxy such as a `.txt` artifact, filesystem mtime, or one ingestion path. A single path failure does not prove the whole pipeline is blocked.

## State-Change Claim → Live System Verification

Before closing or marking-done a task that claims an infrastructure/resource state change, verify the live state, not just the attempted command. "Issued the teardown" is not proof that a service, k8s resource, container, or process is actually gone.

## Binary/rendered artifact completeness

R020 now explicitly rejects text-grep-only completion for redaction, identifier removal, secret scrubbing, content cleanup, and migration cleanup. Completion evidence must include relevant rendered images, PDFs, binary blobs, embedded metadata, or EXIF when those surfaces can carry the same content. The rule also recommends a single pre-rewrite inventory of case variants, substrings/hostnames, binary/rendered artifacts, and reference/orphan status to avoid repeated irreversible rewrites.


## Verification Delegation — Direct Ground Truth First

Direct ground truth is primary: inspect authoritative diffs, files, tests, registries, and APIs before deciding whether a verifier needs another turn. Missing or malformed PASS/FAIL phrasing is not itself a reason to resume a delegate and cannot invalidate sufficient canonical evidence.

Resume only when direct evidence exposes unfinished verification, an incomplete diagnosis, or a concrete evidence gap the same delegate can close. Otherwise synthesize the verdict locally and continue; formatting-only resume loops are prohibited.
